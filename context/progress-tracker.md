## Decisions Made During Build

- **Resume-upload feedback made independent of the server round trip entirely (2026-08-04).** After three rounds of fixes (startTransition, signed URLs, pdf-parse worker) the user still couldn't see any confirmation on screen that a file had uploaded — specifically asked to at least see the uploaded file's name. Rather than keep chasing the exact Next.js revalidation timing without a live repro, added `uploadedFileName` state in `ResumeUpload.tsx` set **synchronously** in `handleFile`, straight from the picked `File` object, before any network call starts — this has zero dependency on the Server Action round trip, `startTransition`, or `revalidatePath` timing, so it cannot be affected by whatever that unresolved race turns out to be. The dropzone text now reads "Uploading `<name>`..." then "`<name>` uploaded" (gated on `resumeUrl` also being truthy, so a failed upload doesn't claim success), and the persisted "Current resume" line now shows the filename too (falls back to the literal `"resume.pdf"` after a page reload, since the original filename isn't persisted anywhere — every upload is stored at the fixed path `${user.id}/resume.pdf` regardless of what the user named the file). The three previous fixes (startTransition, signed URL backstop via render-time prop sync, pdf-parse worker path) are kept as-is — this is additive, aimed at the one thing guaranteed not to race: client-only state set before the `await`.
- **Resume-upload UI still didn't update after the startTransition fix — added a render-time prop sync as a backstop (2026-08-04).** Two real, separate bugs (the pdf-parse worker 404 and the private-bucket signed URL) were found and fixed in between retests, but the original "no visible update after upload" symptom persisted through both. Could not get a definitive browser-console capture from the user to pin the exact mechanism, so rather than keep guessing at Next.js's exact revalidatePath/startTransition interaction, made `ResumeUpload`'s local `resumeUrl` state robust to it regardless of cause: `initialResumeUrl` is compared against its previous value during render (React's documented pattern — `you-might-not-need-an-effect`'s "adjusting state when a prop changes", not a `useEffect`, since `react-hooks/set-state-in-effect` flags synchronous setState-in-effect) and `resumeUrl` is re-synced whenever it changes. Since `uploadResume`'s `revalidatePath("/profile")` is documented to push a refresh of this page's server-rendered props independently of the client's own optimistic update, this guarantees the UI reflects the real DB state on the next render regardless of whether the optimistic `setResumeUrl` in `handleFile` lands correctly. The `startTransition` fix from the previous entry is kept (still correct per the Server Actions docs), this is additive, not a replacement.
- **Reverted stray `proxy.ts` auth bypass (2026-08-04).** `// TEMP-SCREENSHOT-BYPASS: pathname === "/profile" ||` had been left in `isProtectedPath` from an earlier session's screenshot verification (per that session's own progress-tracker note claiming it reverted this "immediately after" — it hadn't). `/profile` was rendering without a login redirect for the whole time since. Restored `pathname === "/profile" ||` as a real (non-commented) check; file is now byte-identical to the last commit.
- **Bug fix — the pdf-parse worker fix from the previous entry took the whole `/api/resume/extract` route down as a 404 (2026-08-04).** `PDFParse.setWorker(require.resolve(...))` via `createRequire(import.meta.url)` ran at module top-level; under Turbopack, `import.meta.url` inside a bundled route resolves to a virtual module path, not a real filesystem location, so `createRequire` built off it can't find `node_modules` and `require.resolve` throws — at import time, outside any try/catch, taking the whole route module down (Next reports this as 404, not 500, since the module never finished loading). Fixed by resolving the worker path from `process.cwd()` (`path.join(process.cwd(), "node_modules/pdfjs-dist/legacy/build/pdf.worker.mjs")` — stable regardless of bundling) instead, and moving the call into a lazy `ensurePdfWorkerConfigured()` invoked inside the `POST` handler's existing try/catch, so any future resolution failure surfaces as a normal JSON 500 instead of silently killing the route. Verified standalone again after the change (same real-PDF extraction test as before, still passes).
- **Bug fix — "View resume" 401'd and "Extract from Resume" 500'd, even after the startTransition fix below (2026-08-04).** Two separate, unrelated root causes surfaced once real end-to-end testing was possible:
  - **Private bucket, public-style URL.** `resumes` is a private bucket (`public: false`, per architecture.md's "authenticated users only, own files only"), but `uploadResume` was storing/returning the bare `upload()` response's `url` field — an authenticated API endpoint, not a directly linkable one. Opening it in a new tab (the "View resume" link) had no Authorization header and failed. Fixed by generating a signed URL (`insforge.storage.from("resumes").createSignedUrl(path, 3600)`) both right after upload (`actions/profile.ts`) and fresh on every `/profile` page render (`app/(app)/profile/page.tsx`) — the stored `resume_pdf_url` column is now only read as an existence flag (a signed URL expires, so the raw stored value can't be trusted as a permanent link); the actual link is always re-signed against the deterministic `${user.id}/resume.pdf` path. Verified live: fetching a signed URL with no auth header returned `200 application/pdf`; the bare API url does not. `library-docs.md`'s Storage section was corrected to match — it previously showed a `getPublicUrl()`/3-arg-`upload()` pattern that doesn't match the installed SDK and doesn't work against a private bucket at all.
  - **pdf-parse worker resolution breaks under Turbopack.** `POST /api/resume/extract` 500'd with `Setting up fake worker failed: Cannot find module '.../.next/dev/server/chunks/pdf.worker.mjs'`. `pdf-parse` v2's Node build (`pdfjs-dist/legacy/build/pdf.mjs`) resolves its worker via a bundler-relative path that Turbopack relocates into `.next/dev/server/chunks`, breaking the dynamic import. Fixed with `PDFParse.setWorker(require.resolve("pdfjs-dist/legacy/build/pdf.worker.mjs"))` (via `createRequire(import.meta.url)`, since the route is ESM) called once before constructing `PDFParse` — an absolute, `require.resolve()`'d path isn't subject to Turbopack's static bundling, so Node loads the real file directly. Verified with a standalone script parsing a real minimal PDF outside the HTTP/auth path (extracted text correctly, no worker error) before touching the route. Referenced `/Users/apple/Projects/GapScan` per the user's pointer — that project sidesteps this entirely by extracting PDF text client-side in the browser (real Worker, loaded from a CDN URL) rather than server-side in Node; kept this project's server-side extraction architecture as-is (matches architecture.md's `app/api/resume/extract` design) and fixed the Node worker resolution instead, since switching architectures wasn't warranted for a bundler config issue.
- **Bug fix — resume upload and profile save silently no-op'd on success (2026-08-04).** After a real upload, InsForge Storage and the `profiles` upsert both completed successfully (verified directly via `insforge logs postgREST.logs`/`insforge.logs` and `insforge db query`), but `ResumeUpload` never showed "Current resume" / "Extract from Resume", and no error banner appeared either — same silent-nothing symptom for `ProfileForm`'s save status banner. Root cause: `uploadResume`/`saveProfile` are Server Actions that call `revalidatePath("/profile")`; per this Next.js version's own docs (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md`: "Updates the UI immediately if viewing the affected path") and the Server Functions convention doc (`.../01-getting-started/07-mutating-data.md`: "By convention, a Server Action is an async function used with `startTransition`. This happens automatically when passed to a `<form>`..."), calling a Server Action directly from a plain event handler — as both `ResumeUpload.handleFile` and `ProfileForm.handleSave` did — without `startTransition` leaves React unable to coordinate the action's own immediate page refresh with the component's local `setResumeUrl`/`setStatus` call, so the optimistic update gets silently dropped (no error, since the underlying `await` genuinely resolved with `{success: true, ...}`). Fixed by wrapping both actions' post-`await` logic in `startTransition` (`useTransition` from `react`) in both components. Two harmless test objects (`resumes/debug-test/resume.pdf`, `resumes/debug-test/resume-big.pdf`) were uploaded to the real InsForge project while reproducing this and were left in place (no CLI object-delete command available) — not referenced by any real profile row.
- 07 AI Profile Extraction from Resume built (2026-08-04), plus a real bug fix in the resume upload it depends on. Two separate things landed together:
  - **Bug fix — resume upload silently no-op'd.** `uploadResume` was called as `uploadResume(file)`, passing a raw `File` straight from a client handler into a Server Action; this never worked, but nothing had exercised it with a real browser session before. Root cause and fix confirmed against Next.js's own docs (`node_modules/next/dist/docs/01-app/02-guides/forms.md`), which consistently use `FormData` for this pattern even for non-`<form>` direct invocation. Client now builds `FormData` and appends the file; `uploadResume(formData: FormData)` extracts and validates it server-side. `ResumeUpload`'s `handleFile` also gained a `try/catch` it never had — previously a thrown/rejected upload left the button stuck on "Uploading..." forever with no error shown.
  - **New: "Extract from Resume" button.** After a resume is uploaded, a button appears (not automatic — explicit user requirement) that calls `POST /api/resume/extract`, which downloads the just-uploaded PDF from Storage, parses it with `pdf-parse` v2's class-based `PDFParse` API (the installed v2.4.5 completely rewrote the old v1 function-call API `library-docs.md` still documents — caught by reading the installed `.d.ts` before writing code, not by a runtime crash), sends the extracted text to Claude, and returns structured JSON. `ProfileForm` was lifted from self-owned state to a controlled `{values, onChange}` component (new `ProfilePageClient` wrapper holds the shared `useState`) so the extraction result can flow into the same form the user is editing, via `mergeExtractedIntoValues()` (`lib/profile.ts`) — which only overwrites fields the resume actually provided, so a user's existing manual edits are never silently clobbered.
  - **OpenAI → Claude API switch, mid-build.** The route was first written against `openai`'s `gpt-4o` (`response_format: json_object`), matching the pattern already used elsewhere. Before it could be verified live, it turned out `OPENAI_API_KEY` in `.env.local` is empty — no funded OpenAI account — while `CLAUDE_API_KEY` is a real key. Rewrote the route on `@anthropic-ai/sdk` (`client.messages.create` with a single forced `tool_choice` call to a `record_profile` tool, the reliable way to get schema-shaped JSON out of the Messages API) and uninstalled `openai`. The live request was verified to reach Anthropic, authenticate, and parse correctly — it was rejected only on account credit balance (`400: "Your credit balance is too low"`), a billing issue, not a code defect. The route's user-facing error message stays generic ("Failed to extract profile data.") rather than surfacing the raw billing error, since that's not actionable from the profile page.
- 06 Profile Save Logic built (2026-08-04) — `actions/profile.ts` (`saveProfile`, `uploadResume`), `lib/profile.ts` (DB↔form mappers + completion calc), `types/index.ts` (new — first use of the file architecture.md had planned but nobody had created yet). Two decisions made without stopping to ask, both documented here per usual practice:
  - **Cover Letter Tone added to the form** (Job Preferences section, paired with Preferred Locations) — feature 05 deliberately left it out to match `profile.png` exactly, but `profiles.cover_letter_tone` is a real CHECK-constrained DB column and 06 is explicitly about wiring the *complete* form to the DB, so leaving a documented required field permanently unmapped wasn't defensible.

The 10-check completion algorithm in `lib/profile.ts` was verified, not guessed: reverse-engineered against `profile.png`'s exact "70%, missing Phone/Location/Education" by testing candidate required-field sets until one reproduced those numbers exactly (7 of 10 checks passing, with LinkedIn/Portfolio counted as required — excluding them does not reproduce 70%).
  - Verified end-to-end against the live InsForge project rather than just type-checking: a scratch script using `createAdminClient` (real existing user id from `auth.users`, found via `db query`) exercised the actual `.upsert([row], {onConflict:'id'})` and `.storage.from('resumes').upload()` calls `saveProfile`/`uploadResume` use, confirmed full round-trip type fidelity (arrays, jsonb, nullables, enums), and specifically confirmed that the resume-only partial upsert does **not** clobber other already-saved profile fields (this was an assumption the plan depended on — PostgREST's `ON CONFLICT DO UPDATE` only touches columns present in the payload — and it held). Separately verified via a real (temporarily-bypassed-proxy) Playwright render that the brand-new-user/no-profile-row path renders cleanly with 0% completion and no forced-empty work experience card.
  - Along the way, confirmed by reading the installed `@insforge/sdk`/`@supabase/postgrest-js` `.d.ts` files directly (not just the skill docs, which disagreed with each other on the storage `.upload()` signature) that `storage.upload(path, file)` is 2-arg with no `upsert` option — overwrite-on-same-path is implicit — and that `database.from(table)` has a native `.upsert(rows, {onConflict})` because it's the real `@supabase/postgrest-js` builder underneath, which none of the InsForge skill docs mention.

- Fixed real post-login redirect loop (2026-08-04) — InsForge logs showed the OAuth code exchange (`POST /exchange`) succeeding on every attempt, but the user still bounced back to `/login`. Root cause was in `proxy.ts`: the protected-route auth check built a `createServerClient()` reading cookies from `response.cookies` (only contains what `updateSession()` itself just wrote, e.g. on a refresh) instead of `request.cookies` (what the browser actually sent, including the fresh `insforge_access_token` from the just-completed login) — so it always saw "no user" and redirected to `/login` even immediately after a successful sign-in. Also stopped `PostHogProviderContent` from calling the browser SDK's `getCurrentUser()` when there's no `insforge_access_token` cookie yet — that call's internal fallback hits the InsForge host directly cross-origin and always 401s for anonymous visitors, which was confusing console noise (visible on every page load, not just after login) but not the actual bug.
