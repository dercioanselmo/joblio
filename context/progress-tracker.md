- **Bug fix — `proxy.ts`'s `requestCookies` had no `.set()`, so a refreshed access token never reached the current request's own Server Components (2026-08-12).** Root cause of the "infinite `/dashboard`/`/find-jobs`/`/` refetch" the user reported repeatedly. Diagnosed by reading `updateSession()`'s actual source in `node_modules/@insforge/sdk/dist/ssr/update-session` (not guessed): it calls `setAuthCookies()` on **both** `requestCookies` and `responseCookies` when it refreshes an expiring token, and `setCookie()` silently no-ops (`if (!cookies?.set) return`) when the target has no `.set`. `proxy.ts`'s `requestCookies` was a plain `{ get }` object — read-only — so that internal call always no-op'd. The refreshed token still reached the *browser* correctly via `responseCookies` (`response.cookies`, a real writable `ResponseCookies`), but every Server Component rendered in the *same* request (`Navbar`, and any page doing its own `createInsforgeServer()` + `getCurrentUser()` check) kept reading the stale, already-expired cookie via `next/headers`, since that request-scoped cookie jar was never updated. Confirmed via temporary diagnostic logging in `proxy.ts` (added, used, then replaced by the real fix — never left in) showing `hadAccessTokenCookie: true` / `refreshed: false` / `gotAccessToken: true` on every request, i.e. the middleware itself always saw a healthy session — the bug was entirely about that session not propagating to the render.
  - Fixed by giving `requestCookies` a real `.set()` that mutates `request.cookies` and rebuilds `response = NextResponse.next({ request })` from it, then applying the same cookie to that fresh `response` afterward — the documented pattern for exactly this problem in Next.js middleware (matches `@supabase/ssr`'s official middleware example precisely, which `@insforge/sdk/ssr` is modeled after). `CookieWriter.set` is overloaded (`(name, value, options)` or a single `{name, value, ...options}` object) even though the library only ever calls the 3-arg form — `normalizeSetArgs()` handles both shapes so the assigned function is structurally valid against the full exported type, no type assertion needed. `.delete()` wasn't implemented since it's optional on `CookieWriter` and the library's own `deleteCookie()` helper prefers `.set()` (an expired cookie) over `.delete()` whenever `.set` exists — confirmed by reading that function too, not assumed.
