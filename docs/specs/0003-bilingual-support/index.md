# 0003. Add English and Portuguese as switchable UI languages

**Date**: 2026-08-13
**Status**: Proposed

## Summary

Joblio's UI (buttons, labels, messages, page copy) will be available in English and Portuguese, with a visible switcher and English as the default. This covers only the app's own written copy. Content the app does not author itself, the AI generated match reasons, company research, and generated resumes, and the Portuguese language job postings pulled from emprego.co.mz (feature 18), stays exactly as it is today in both languages. The app gains a locale segment in every URL (`/en/...`, `/pt/...`) so each language has its own real, shareable link.

## Requirements

**User stories**:
- As a Portuguese speaking job seeker in Mozambique, I want the app's own interface (buttons, labels, messages) in Portuguese, so I can use it comfortably in my own language.
- As any user, I want a visible, one click way to switch language from any page, so I am never stuck in the wrong one.
- As a first time visitor, I want the app to default to English until I choose otherwise, so behavior is predictable.

**Acceptance criteria**:
- **AC-1**: Every page's static UI chrome (navbar, buttons, form labels, headings, empty/error/success messages, homepage and marketing copy) renders in English or Portuguese according to the active locale.
- **AC-2**: Every existing route is reachable under a locale prefixed URL, `/en/...` and `/pt/...`; there is no unprefixed route.
- **AC-3**: A language switcher is visible in the navbar on every page and lets the user move to the equivalent page in the other language in one click.
- **AC-4**: A visitor with no stored language preference (first visit, or an expired cookie) sees English.
- **AC-5**: Once a user switches language, later visits within the cookie's lifetime keep that choice without switching again.
- **AC-6**: An unsupported locale segment in the URL (for example `/fr/dashboard`) redirects to the same page under the default language (English), not a 404.
- **AC-7**: A signed out visit to a protected page still redirects to the login page, and that redirect keeps the locale the visitor was already on (a Portuguese session sends them to `/pt/login`, not `/en/login`).
- **AC-8**: AI generated content (match reasons, company research dossiers, generated resumes) is never translated; it stays in whatever language it was generated in (English, per the existing agent prompts), regardless of the UI's active locale.
- **AC-9**: Job data sourced from emprego.co.mz (title, company, location, role overview, responsibilities, requirements) is displayed exactly as stored, in Portuguese, regardless of the UI's active locale. It is never run through translation.
- **AC-10**: A missing or not yet written translation for a given key falls back to its English text rather than showing a raw key or crashing the page.

## Decision

**Chosen option**: Option 2: Adopt `next-intl` with locale prefixed routing

The app moves every route under a `[locale]` URL segment (`/en/...`, `/pt/...`), using `next-intl`, the standard i18n library for the Next.js App Router. The active locale's preference is stored in a cookie only (no database change). Language switching is a plain link to the same page under the other locale prefix; `next-intl`'s own middleware sets the cookie when that link is followed. Translation covers only the app's own static UI copy; AI generated content and emprego.co.mz job data are explicitly out of scope for translation (AC-8, AC-9).

Reasoning and options considered: see `rationale.md`.

## Feature design

**Data model sketch**:

None. No new table or column. The active locale is carried entirely by the URL and a `NEXT_LOCALE` cookie that `next-intl`'s middleware reads and writes; nothing is persisted server side.

**API surface**:

No new endpoints. This is a routing and rendering change; switching language is a navigation, not an API call.

**Value sourcing**:

| Action | Value produced / displayed | Source |
|---|---|---|
| Render any page | the active locale (`en` or `pt`) | the URL's locale segment, resolved by `next-intl`'s middleware from the `NEXT_LOCALE` cookie, defaulting to `en` when absent or unsupported (AC-4, AC-6) |
| Render any page | the translated text for a given UI string | `messages/<locale>.json`'s matching key; falls back to `messages/en.json` when the key is missing in the active locale (AC-10) |
| Click the language switcher | the URL to navigate to | the current pathname with only the locale segment swapped, generated by `next-intl`'s locale aware `Link` (AC-3) |
| Signed out visit to a protected page | the login redirect URL | `proxy.ts`'s existing redirect target, with the active locale segment preserved instead of dropped (AC-7) |
| Render a job card or job details page | job title, company, location, role overview, responsibilities, requirements | the `jobs` table row exactly as stored (unchanged from feature 18), never translated (AC-9) |
| Render a match score, research dossier, or generated resume | the AI generated text | `agent/matcher.ts` / `agent/research.ts` / resume generation, unchanged, always English (AC-8) |

**Key invariants**:
- Every route exists under exactly two locale prefixes, `en` and `pt`; there is no route reachable without one.
- `proxy.ts`'s protected path check runs against the pathname with the locale segment stripped, so `/pt/dashboard` is protected exactly like `/en/dashboard` is today.
- AI generated content and emprego.co.mz sourced job fields are never passed through a translation step, in either direction.
- A translation key that exists in `messages/en.json` but not yet in `messages/pt.json` never breaks the page; it falls back to the English string.

**Security model**: Unchanged from today. `proxy.ts` still gates the same three protected paths (`/dashboard`, `/profile`, `/find-jobs`); the only change is comparing against the de-prefixed pathname so the check keeps working once every route carries a locale segment.

**Configuration required**: None. No new environment variables; `next-intl`'s locale list (`en`, `pt`) is a code level constant, not a secret.

**Critical test scenarios**:
- Happy path: switch to Portuguese from the navbar on any page, land on the same page under `/pt/...` with all chrome translated, verifies **AC-1**, **AC-3**.
- Happy path: open a job found via emprego.co.mz while the UI is set to Portuguese, confirm the job's own title/description stays exactly as scraped (already Portuguese) and no AI generated match reason gets translated, verifies **AC-8**, **AC-9**.
- Failure case: sign out, visit `/pt/dashboard` directly, confirm the redirect lands on `/pt/login`, not `/en/login`, verifies **AC-7**.
- Edge case: visit `/fr/dashboard`, confirm it redirects to `/en/dashboard` rather than a 404, verifies **AC-6**.

## Build plan

Per this project's stated build approach (`context/build-plan.md`'s Core Principle: "every feature must be visible and testable before moving on, no invisible phases"), this is applied here as a thin end to end slice first: get one full path (routing plus middleware plus navbar plus one page) working and visibly verified in both languages, then extend page by page, rather than wiring every page's strings before anything is checkable.

1. Add `next-intl` to `context/code-standards.md`'s approved dependencies and install it, satisfies **AC-1**, **AC-2**
2. Configure `next-intl`: locale list (`en`, `pt`), default `en`, `localePrefix: "always"`, and the routing config it needs, satisfies **AC-2**, **AC-4**, **AC-6**
3. Move the route tree under `app/[locale]/` (root layout, homepage, `(app)/`, `(auth)/`), wrap the root layout in `next-intl`'s provider, satisfies **AC-2**
4. Chain `next-intl`'s middleware into `proxy.ts`: resolve the locale first, then run the existing protected path check against the de-prefixed pathname, and make the login redirect carry the active locale, satisfies **AC-6**, **AC-7**
5. Create `messages/en.json` and `messages/pt.json`, seed both with the navbar's strings, build the navbar's language switcher as a locale swapping link, satisfies **AC-1**, **AC-3**, **AC-5**
6. Translate the homepage's copy into both message files and verify the full slice (routing, middleware, switcher, one real page) live in both languages before extending further, satisfies **AC-1**, **AC-10**
7. Extract and translate Dashboard, Profile, Find Jobs (search controls, filters, sort labels, empty/error/success messages), and Job Details page chrome into both message files, satisfies **AC-1**, **AC-10**
8. Verify live that emprego.co.mz sourced job fields and AI generated content (match reasons, research dossiers, resumes) render unchanged in both locales, satisfies **AC-8**, **AC-9**
9. Update `context/ui-registry.md`, `context/progress-tracker.md`, and `context/build-plan.md`'s feature 19 entry

## Consequences

**Positive**:
- The app becomes genuinely usable for Portuguese speaking users in its actual target market (Mozambique), not just its job data.
- Each language gets a real, shareable, bookmarkable URL rather than a stateful toggle that changes what a shared link shows.
- Scope stays contained: AI content and job board data are explicitly excluded from translation, so this doesn't reopen `agent/matcher.ts` or `agent/research.ts`.

**Negative / tradeoffs**:
- Every route moves under a `[locale]` segment, a structural change touching the whole `app/` tree and `proxy.ts`'s path matching; this is the widest reaching change since the project's original scaffold.
- A Portuguese UI user still reads AI generated match reasons, dossiers, and resumes in English (AC-8); this is a deliberate scope cut for this feature, not a limitation of `next-intl`.
- The message files (`messages/en.json` / `messages/pt.json`) are a new translation surface that every future page must extend; skipping a key silently falls back to English (AC-10) rather than failing loudly, which can hide an untranslated string during development.
- No automated translation quality check exists; a wrong or awkward Portuguese string ships unless someone reviews it.

**Neutral**:
- No database migration; locale is cookie only, so there is nothing to backfill or roll back at the data layer.
- Existing `jobs` rows and AI generated content are untouched by this feature; nothing about feature 18 or the matching/research pipeline changes.

## Migration plan

**Strategy**: Direct replace, single deploy, no feature flag. There is no live traffic depending on unprefixed URLs staying unprefixed (this is a low traffic pre launch app), which is what makes moving every route under `[locale]` in one change acceptable rather than requiring a strangler rollout.
**Phases**:
1. Build and verify the thin end to end slice (routing, middleware, navbar, homepage) in both languages before extending further (build plan tasks 1 to 6).
2. Extend translation page by page (Dashboard, Profile, Find Jobs, Job Details), verifying each live before moving to the next (build plan tasks 7 to 8).
**Rollback**: Revert the commits; no data migration occurred, so reverting is complete. A user's `NEXT_LOCALE` cookie simply stops being read once the code is reverted.
**Risks**: Moving every route under `app/[locale]/` risks breaking an existing absolute path reference (a hardcoded `href`, a redirect, an email link) that assumes no locale prefix. The build should grep for hardcoded internal links before considering each page's slice done, not rely on typechecking alone to catch it.
